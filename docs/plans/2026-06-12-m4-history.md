# M4 — Version history

**Owner:** Mikhail (Javid inactive) · **Status:** done (PR #5) · **Branch:** `feat/m4-history`

## Goal

Every generation and edit becomes a browsable **version**: a History panel lists
them (newest first) with status, and any succeeded version can be loaded back
into the viewer — compare results, return to an earlier model, branch a new edit
off an old version. Works without Mongo (in-memory, session-scoped) and uses the
persisted records when a DB is connected.

## API contract (server)

`GET /api/history` → `200 { entries, source }` where `source` is `"db"` or
`"memory"` and each entry is:

```json
{
  "kind": "generate | edit",
  "taskId": "…",
  "prompt": "text sent to the generator",
  "instruction": "edit-only",
  "regionLabel": "edit-only",
  "status": "PENDING | IN_PROGRESS | SUCCEEDED | FAILED | CANCELED",
  "modelUrl": "GLB url when SUCCEEDED",
  "mock": true,
  "createdAt": "ISO 8601"
}
```

Newest first, capped at 50.

## Behavior

- `services/history.js` — in-memory ring buffer (last 100) recorded on every
  task creation and updated on terminal polls; the session-scoped fallback.
- With Mongo: listing merges `GeneratedModel` + `SpatialPromptRecord` rows into
  the same shape. `SpatialPromptRecord` gains `status`/`modelUrl`; the poll route
  updates both collections on terminal statuses.
- Client `HistoryPanel`: fetches on mount and whenever a task starts/finishes;
  each succeeded entry has a Load button → model into the viewer, its prompt
  becomes the base-model context (so edits can branch off old versions).

## Acceptance criteria

1. `npm --prefix client run build` passes.
2. No DB: generate + edit in mock mode → `GET /api/history` lists both entries
   (`source: "memory"`), edit first, with correct kind/status; after the tasks
   finish, statuses read SUCCEEDED with modelUrl.
3. UI: History panel shows entries live; Load on an old version swaps the viewer
   and sets its prompt as base context; Load disabled while a task runs. (manual)
4. With Mongo: same list served from the DB (`source: "db"`), surviving server
   restarts. (manual, needs DB)

## Out of scope (M5)

- Evaluation of edit quality, spatial-vs-plain prompt comparison, dataset export.
- Diff/preview between versions (only load-and-look).

## Risks

- Memory history is per-server-process — restarting the dev server clears it
  (by design; Mongo covers persistence).
- Real Meshy model URLs are time-limited signed URLs — old persisted versions
  may stop loading after expiry. Follow-up for M5: download/proxy GLBs
  server-side if long-lived history matters.
