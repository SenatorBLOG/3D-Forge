# M2 — Meshy AI integration: text-to-3D pipeline

**Owner:** Mikhail (Javid inactive this week) · **Status:** done (PR #3) · **Branch:** `feat/m2-meshy`

## Goal

A user types a prompt ("a small dragon"), the server creates a Meshy text-to-3D
preview task, the client polls progress, and when the task succeeds the generated
GLB loads straight into the viewer (which M1 made source-agnostic). Without a
`MESHY_API_KEY`, a built-in mock simulates the same lifecycle using the bundled
robotic hand — the full pipeline stays demoable with zero external credits.

## API contract (server)

- `POST /api/generate` body `{ "prompt": string }` → `202 { taskId, mock }`
  - 400 on missing/empty prompt or prompt > 600 chars (Meshy limit)
  - 502 when the upstream service fails
- `GET /api/generate/:taskId` → `200 { taskId, status, progress, modelUrl }`
  - `status`: Meshy values `PENDING | IN_PROGRESS | SUCCEEDED | FAILED | CANCELED`
  - `modelUrl`: GLB url when `SUCCEEDED`, else null; 404 unknown task (mock mode)

Upstream (per https://docs.meshy.ai/en/api/text-to-3d):
`POST https://api.meshy.ai/openapi/v2/text-to-3d` `{mode:"preview", prompt}` →
`{result: <taskId>}`; `GET .../text-to-3d/:id` → task with `status`, `progress`,
`model_urls.glb`. Auth: `Authorization: Bearer $MESHY_API_KEY`.

## Acceptance criteria

1. `npm --prefix client run build` passes.
2. Mock mode (no key): `POST /api/generate {"prompt":"a dragon"}` → 202 with taskId;
   polling shows progress climbing; within ~10s status `SUCCEEDED` with a modelUrl.
3. Validation: empty prompt → 400; prompt over 600 chars → 400.
4. Unknown task id → 404 (mock mode).
5. UI: Generate panel with prompt + button; button shows live progress %; on success
   the viewer swaps to the generated model. (manual)
6. Mongo persistence: when a DB is connected, each generation is saved and
   `GET /api/models` returns it; without a DB everything still works.

## Tasks

1. `server/src/services/meshy.js` — Meshy client (fetch, Bearer auth) + mock task
   simulator (id map, time-based progress, resolves to `/models/robotic_hand.glb`).
2. `server/src/models/GeneratedModel.js` — mongoose schema: prompt, meshyTaskId,
   status, modelUrl, mock, timestamps.
3. `server/src/routes/generate.js` — implement POST (create task, validate, persist
   when dbReady) and GET /:taskId (poll, map to contract, update DB on terminal).
4. `server/src/routes/models.js` — return last 50 saved generations when dbReady.
5. `client/src/components/GeneratePanel.jsx` — prompt form, 2s polling, progress on
   the button, error display, `onModelReady(url)` → `swapModel`.
6. `App.jsx` wiring + styles; `.env.example` note about mock mode; ARCHITECTURE.md
   status update.

## Out of scope (follow-ups)

- Meshy `refine` mode (textures) — preview output is enough for the pipeline.
- Downloading/caching generated GLBs server-side (Meshy URLs expire eventually).
- History UI for saved generations (uses `GET /api/models`, part of M4).

## Risks

- Real-mode behavior can't be CI-tested without a key/credits; mock mode mirrors the
  documented contract, but the first live run with a real key needs a manual check.
- Meshy GLB URLs are remote — viewer loads them cross-origin; Meshy serves CORS-enabled
  assets, but if that changes we'd need a server-side proxy (follow-up noted above).
